| `ANTHROPIC-PROMPTING-01` | Anthropic | [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) | Be clear and direct: be specific about the desired output format and constraints, give sequential steps as numbered lists where order or completeness matters, and apply the golden rule — "Show your prompt to a colleague with minimal context on the task and ask them to follow it. If they'd be confused, Claude will be too." Add context: explaining *why* a constraint matters ("your response will be read aloud by a text-to-speech engine, so never use ellipses") outperforms stating the constraint alone. Use examples effectively: few-shot/multishot examples should be relevant, diverse, and wrapped in `<example>` tags (multiple in `<examples>`), with 3–5 examples recommended. Structure prompts with XML tags: wrap each content type in its own tag (`<instructions>`, `<context>`, `<input>`), use consistent descriptive tag names, and nest where content has a natural hierarchy. Give Claude a role: a role set in the system prompt, even one sentence, focuses behaviour and tone. Long context prompting: place longform data near the top, above the query/instructions/examples, and wrap multiple documents in `<document>` tags with `<document_content>`/`<source>` subtags. Agentic systems: long-horizon work needs explicit state tracking, autonomy must be balanced against safety, and complex prompts should be chained into steps. |
| `OPENAI-PROMPTING-01` | OpenAI | [Prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering) (the older `https://platform.openai.com/docs/guides/prompt-engineering` URL redirects here) | Message roles and instruction following: the `instructions` parameter and the `developer`/`user`/`assistant` roles carry differing levels of authority. Few-shot learning: including a handful of input/output examples steers the model toward a new task without fine-tuning. Message formatting with Markdown and XML: organise a developer message into Identity, Instructions, Examples, and Context sections using Markdown headers and XML tags. Include relevant context information: retrieval-augmented generation via vector databases or file-search tools constrains responses to specific resources. Prompt caching: position frequently-reused content at the beginning of the prompt for cost and latency savings. Prompting reasoning models vs. GPT models: reasoning models work from high-level goals, while GPT models need "precise instructions that explicitly provide the logic and data required." Tool-use examples: concrete function-invocation examples improve reliability. |
| `GOOGLE-PROMPTING-01` | Google | [Prompt design strategies (Gemini API)](https://ai.google.dev/gemini-api/docs/prompting-strategies) | Give clear and specific instructions; frame the input as a question, task, entity, or partial completion; specify constraints on reading the prompt or generating the response, including what not to do; define the response format (table, list, paragraph) explicitly. Add few-shot examples rather than relying on zero-shot for pattern-sensitive tasks. Add contextual/background information the model needs. Break down complex prompts into components — decompose instructions, or chain sequential prompts. Iterate: rephrase with alternative vocabulary, switch to an analogous framing, and reorder prompt content when results don't match. Use structured formatting (XML tags or Markdown) to separate instructions, context, and task. Agentic workflows: instruct explicit planning before action, with deliberate reasoning frameworks for complex tasks. Generation-parameter tuning (temperature, topK, topP, max tokens) and grounding tools (Search, code execution) are also covered but are API-level controls with no equivalent in a chat invocation of an Agent Skill. |
| `BYTEPLUS-PROMPTING-01` | BytePlus | [Prompt engineering (ModelArk)](https://docs.byteplus.com/en/docs/ModelArk/prompt-engineering) | Evaluation first: establish success criteria and an evaluation before iterating on a prompt. Model-strategy fit: deep-thinking models should be given goals and constraints and left to plan, while non-deep-thinking/templated-task models need explicit steps, formats, and examples. Iteration loop: Update → Test → Debug → Evaluate, with prompt versioning. Structured content: organise the prompt into `# Identity`, `# Instructions`, `# Examples`, and `# Context` Markdown sections so the model knows where the rules, examples, and reference material are. Roles: put stably-reused information early (system/instructions) and task-specific information later. General-task template: specify role, context, and task, give explicit numbered rules, at least two worked Question/Output example pairs, and explicit output-format requirements. Agent scenarios: planning and persistence (split into subtasks and track completion), transparency (briefly explain the reason for a tool call before key steps), and progress management (TODO/rubric-style tracking). |

## Cross-provider convergence

Three techniques are documented independently by all four publishers above, which is why skills in this repo treat them as settled rather than as one vendor's house style:

| Technique | Anthropic | OpenAI | Google | BytePlus |
|---|---|---|---|---|
| Structural separation of instructions / context / examples / input | XML tags (`<instructions>`, `<context>`, `<input>`), nested where hierarchical | Identity / Instructions / Examples / Context via Markdown headers and XML tags | "XML tags or Markdown" to separate instructions, context, and task | `# Identity` / `# Instructions` / `# Examples` / `# Context` Markdown sections |
| Few-shot examples | 3–5, relevant + diverse, in `<example>`/`<examples>` tags | "a handful of input/output examples" | zero-shot vs. few-shot, examples demonstrating the desired pattern | at least two worked Question/Output pairs in the general-task template |
| Match instruction precision to the model's reasoning mode | — (covered as model-specific guidance per Claude model) | reasoning models take high-level goals; GPT models need precise explicit logic and data | — | deep-thinking models get goals and constraints; non-deep-thinking models get explicit steps and formats |

The four-way agreement on the first row and the independent two-source agreement on the third are the strongest claims in this ledger. The remaining techniques — role setting, stating the reason behind a constraint, long-context placement, decomposition/chaining, iteration loops with versioning, evaluation-before-iteration, and agentic state tracking — are each carried by one or two of the four and are attributed to those specifically rather than presented as consensus.
